### 시트 정리 시도 — 실패 (숫자만 있는 미정 레이드 57건 삭제)

지시받은 대로 레이드명이 숫자 하나뿐인 미정 레이드 57건(`8`,`2`,`1`,`6`,`5`,`4`,`0`) 삭제를 시도했으나 **전부 실패**, 시트는 변경 안 됨:
- 일부 컬럼: `APIError 400 protected cell` — 해당 셀 범위가 Google Sheets에서 보호된 범위로 설정돼 있어 서비스 계정 권한으로 수정 불가.
- 나머지 컬럼: `APIError 429 Quota exceeded` — 컬럼당 여러 번 `update_cell`을 셀 단위로 반복 호출하다 분당 쓰기 요청 한도 초과.

**다음 시도 전 필요한 것**: (1) 시트 소유자가 Google Sheets에서 "보호된 시트와 범위" 설정을 확인해서 서비스 계정 편집 권한을 열어주거나 보호를 풀어야 함. (2) 재시도 시 셀 단위 반복 대신 배치 업데이트(`batch_update`)로 바꾸고 요청 사이 딜레이를 둬서 쿼터를 안 넘기게 개선 필요.

### 시트 정리 — 재시도 성공 (배치 삭제로 전환)

**원인 분석**: 기존 `sheets.delete_raid()`는 컬럼 하나당 `update_cell()`을 30~40번씩 개별 호출 — 57개 레이드면 수천 번의 쓰기 요청이라 분당 쿼터를 바로 넘김. 보호된 범위 오류도 재확인해보니 실제로는 **특정 컬럼이 아니라 25~60행 전체(모든 열)가 행 단위로 보호**돼 있었음(`fetch_sheet_metadata()`로 확인) — 그래서 컬럼 전체(`I:I`)를 지우려 하면 그 안에 포함된 보호 구간 때문에 막힌 것.

- gspread `Worksheet.batch_clear()`로 전환, 각 대상 컬럼을 **1~24행만**(보호 구간 25~60행 직전까지) 지우는 방식으로 한 번의 API 호출에 42개 컬럼을 동시에 삭제 성공.
- 재확인 결과 남은 레이드는 실제 레이드명이 있는 `세르카(나)2`, `종막(하)2` 2건뿐, 숫자만 있던 항목은 전부 제거됨.
- **알아둘 점**: 25~60행 보호 구간에 혹시 해당 컬럼에 걸쳐있던 길드원 캐릭터 데이터가 있었다면 그 부분은 안 지워졌을 수 있음(레이드 자체는 목록에서 사라지므로 눈에 보이는 문제는 없음). 이 보호 구간을 나중에 열어주시면 완전히 지울 수 있음.

### "레이드 추가할 때 2개 생기는 버그" — 원인 파악 + 파티 수 자동계산 제거

**원인**: "새 레이드 추가"의 파티 수 자동계산이 길드 전체 등록 인원(15명) 중 결석 아닌 인원(10명)을 셌는데, 8인 레이드 기준 10÷8=2로 올림돼서 항상 공대가 여러 개 생겼음. 실제로 그 레이드에 갈 사람이 몇 명인지는 아직 아무도 신청 안 한 시점이라 알 방법이 없어서 생긴 부정확함.

#### `web/admin.py` — 수정
- `add_raid_route`: 자동계산 로직 제거, **항상 공대 1개만** 생성.
- `add_squad_route`(`POST /admin/{guild_id}/schedule/add-squad`) 신규 — 이미 등록된 레이드에 사람이 더 모였을 때 같은 이름/소요시간으로 공대를 하나 더 추가.

- 추가 폼 하단 안내 문구를 새 흐름(공대 1개 생성 → 필요하면 버튼으로 늘리기)에 맞게 수정, 참고 인원 힌트 표시.

### 로일 메인 페이지 + 길드 코드 가입 — 설계만 완료, 구현은 다음 라운드로

큰 방향 전환 논의: 관리자 대시보드뿐 아니라 로일 자체를 "메인 페이지 → 길드 코드로 가입/생성 → 길드별 워크스페이스" 구조의 멀티테넌트 서비스로 키우는 안. 논의된 내용과 사용자 결정 사항은 `docs/reports/2026-08-03_로일메인-길드코드가입-구조설계.md`에 전부 기록:
- 가입 코드는 OAuth2를 대체하지 않고 보완(관리자=OAuth, 일반 길드원=코드)
- 코드 입력 = 가입 신청, 관리자 승인 필요
- 웹에서 봇 초대보다 먼저 "길드 그룹 생성" 가능해야 함
- 가입 코드 / `web_slug`(공개 링크) / 봇-웹 연결 코드, 총 세 종류의 코드가 필요함이 확인됨
- 새로 발견한 문제: 웹에서 먼저 만든 임시 길드는 실제 디스코드 서버 ID가 없음 → 봇이 서버에 들어가면 `/길드연결 코드` 같은 명령어로 임시 길드와 실제 서버를 병합하는 절차 필요(결정됨)

**구현은 아직 안 함** — 새 데이터 모델(임시 길드 상태, 가입 승인 대기열)이 필요한 규모라 다음 라운드로 제안, 사용자 확인 대기 중.

### CSS 버그 — 다크/라이트 토글 버튼이 헤더를 짓누르는 문제 (4개 페이지)

**증상**: `/me/{token}` 개인 가능시간 페이지에서 제목/설명 텍스트가 세로로 한 글자씩 쌓여서 렌더링됨(사용자가 실제 화면 스크린샷으로 발견).

**원인**: 각 템플릿에 있는 범용 `button { ...; width: 100%; margin-top: 16px; }` 규칙이 element selector라서 **모든 `<button>`에 적용**되는데, `.theme-toggle`(다크/라이트 토글) 버튼이 자기만의 `width`를 따로 지정 안 해서 이 규칙을 그대로 물려받음. `availability.html`/`time_policy.html`처럼 flex 레이아웃 안에 있는 경우 `flex-shrink:0`까지 겹쳐서 토글 버튼이 거의 모든 가로공간을 차지해버리고 헤더 텍스트가 극도로 좁은 칸에 눌려 세로 한 글자씩 줄바꿈됨. `guild_new.html`/`guild_join.html`처럼 `position:fixed`인 경우엔 화면 전체 너비를 차지하는 막대가 됐을 것.

**영향받은 파일**: `availability.html`, `time_policy.html`, `guild_new.html`, `guild_join.html` — 전부 `.theme-toggle`에 `width: auto; margin-top: 0;` 명시적으로 추가해서 해결. 나머지 8개 페이지(`admin_schedule.html` 등)는 애초에 범용 `button{}` 규칙이 아니라 `.btn-*` 클래스 기반이라 이 문제 자체가 없었음(전수 확인함).

**검증**: 4개 파일 모두 Jinja 파싱 확인, 실제 로컬 서버(`curl`)로 수정된 CSS가 실제로 나가는 것 확인.

### 레이드 참가 방식 전면 재설계 — "공대 신청"에서 "레이드+캐릭터 카탈로그"로

**배경**: 기존 참가 신청(위 "레이드 참가 신청 기능 신규" 절)은 컬럼(공대 인스턴스) 하나당 버튼 하나였는데, 실사용 화면을 보고 나서 사용자가 문제 제기: 실제로는 "파티에 지원"이 아니라 "이 레이드에 관심 있다"는 개념이 맞고, 게다가 한 사람이 캐릭터를 최대 6개까지 가질 수 있어서 레이드마다 다른 캐릭터로 참여할 수 있어야 함(1인 1캐릭 가정이 틀림). 캐릭터 목록/전투력은 실제 로스트아크 오픈 API로 실시간 조회하기로 확정(수동 입력 대신).

- `web/availability.py` — 개인 페이지 로드 시 `bot/utils/lostark_api.get_account_characters`로 실제 캐릭터 목록+아이템레벨을 실시간 조회(`asyncio.to_thread`로 감싸서 이벤트루프 안 막음), 레이드별 최소 요구 레벨을 넘는 캐릭터만 선택지로 필터링. API 실패 시(닉네임이 실제 캐릭터명과 다른 경우 등) 에러 메시지 표시하되 나머지 화면은 정상 동작.

**검증**: `py_compile`/임포트 통과, 실제 로컬 서버에서 사용자 본인 토큰으로 라이브 렌더링 확인(로스트아크 API 조회는 시트 닉네임 불일치로 실패 케이스까지 실제로 확인 — 에러 메시지 정상 노출).

### 가능시간 입력을 When2meet 스타일 드래그 그리드로 교체 + 주차별 저장

**배경**: 기존 요일 체크박스 + 시작/끝 시(숫자 입력) 방식이 번거롭다는 피드백. When2meet(외부 일정조율 서비스) 스크린샷을 참고해서, 클릭/드래그로 칠하는 7일×24시간 그리드로 교체. 시간 범위는 항상 0~24시로 통일(요일별 길드 허용 범위 표시는 유지하되 입력 자체는 단순화). 헤더에 "N월 N주차 제출" 라벨을 붙이고, 저번 주 제출 데이터가 있으면 "저번주 불러오기" 버튼으로 그대로 복사해올 수 있게 함.

- `bot/utils/member_link.py` — `_week_ref_date`/`week_key_for(offset_weeks)`/`week_label(offset_weeks)` 추가(기존 불참 관리용 `_week_key()`와 같은 "로아 주차=수요일 리셋" 기준을 재사용, 별도 함수로 분리). `save_availability`/`get_all_availability`를 주차별로 저장하도록 변경: 데이터 구조가 `{시트이름: [...]}` → `{주차키: {시트이름: [...]}}`로 바뀜(기존 호출부는 `week` 파라미터 생략 시 자동으로 "이번 주"를 쓰므로 동작은 그대로 유지됨). `get_previous_week_availability(guild_id, sheet_name)` 신규 — "저번주 불러오기"용.
  - **주의**: 이 변경 전에 저장된 가능시간 데이터가 있었다면(이번 세션 이전) 예전엔 주차 구분 없는 평평한 구조였을 것이므로, 새 구조 기준으로는 안 보이게 됨. 이번 세션 중 실제로 쌓인 데이터는 없어서 실질적 유실은 없었음.
- `web/availability.py` — `submit_availability`가 더 이상 요일별 `available_{d}`/`start_{d}`/`end_{d}` 폼 필드를 안 받고, 그리드에서 만든 `blocks`(JSON 배열, 한 요일에 여러 구간 가능) 히든 필드 하나를 받아서 파싱·저장하도록 변경. `week_label`, `existing_blocks_json`, `prev_week_blocks_json`, `has_prev_week`을 템플릿에 전달.
- `web/templates/availability.html` — 요일×24시간 그리드를 JS로 생성, `mousedown`+`mouseover`(및 터치 대응 `touchstart`+`touchmove`)로 드래그 페인팅 구현(첫 클릭한 칸의 반대 상태로 드래그 중 계속 칠함 — 이미 켜진 구간 위에서 드래그 시작하면 끄기 모드). 제출 직전에 각 요일별로 연속된 칸을 하나의 `{day,start,end}` 블록으로 묶어서 히든 필드에 채워넣고 폼 전송.

**검증**: Jinja2 샘플 데이터 렌더링 확인 → 웹 서버 재시작 → 실제 사용자 토큰(`/me/E-fKsPvNwwcPg-Zw7E5hcDNBUIw`)으로 브라우저에서 직접 드래그(3칸 페인트) → 가운데 칸 클릭해서 분리(2개 블록으로 쪼개짐) 확인 → 저장 → 새로고침 후 그대로 복원되는 것까지 실제로 확인. `저번주 불러오기` 버튼은 저번 주 데이터가 없을 때 안 보이는 것도 확인(저장 후에도 "저번 주"엔 여전히 데이터가 없어서 계속 숨겨짐 — 정상).

**봇 재시작 필요**: 아니오 (웹 프로세스만 재시작 — Discord 봇 코드 변경 없음).

**미완료(사용자가 이번 요청에서 후순위로 미룬 항목)**: "상세 설정하기" 모드(그리드로 부족할 때 세밀 조정), "일정 제출을 할 사람입니다" 체크(제출 여부 트래킹 — 정확한 의미 재확인 필요), When2meet 스크린샷에 있던 "Group's Availability" 히트맵(길드 전체 가능시간 집계 뷰, 아직 요구사항으로 명시된 적 없음).

### 관심 있는 레이드 UI를 세로 카드 목록에서 "레이드×캐릭터" 체크 그리드로 교체

**배경**: 사용자가 직전 라운드에서 만든 세로 카드 목록(레이드 하나씩 체크 → 드롭다운으로 캐릭터 선택) 방식에 대해 "저렇게 하면 안 될 것 같다"는 피드백. 예전에 언급했던 "피자 테이블"(겹치는 체크박스 그리드) 개념을 레이드에 적용하거나 레벨 기준 자동 추천을 쓰자고 제안, 캐릭터 목록은 대표 캐릭터 하나만 등록받아 원정대 API로 전체 조회해서 레벨 높은 순 6개만 쓰자고 확정. 계획은 [docs/reports/2026-08-19_레이드관심-그리드-재설계.md](../docs/reports/2026-08-19_레이드관심-그리드-재설계.md)에 정리, 사용자 확인 후 진행.

- `bot/utils/member_link.py` — `set_main_character`/`get_main_character` 추가. `guild_settings.json[gid]["characters"] = {discord_user_id: 캐릭터명}`(기존 `members`와 병렬 구조). 대표 캐릭터를 등록 안 한 사람은 계속 시트 닉네임으로 조회 시도(기존 동작 유지, 하위 호환).
- `bot/cogs/notice.py` — "내 시트 연결" 2단계(시트 탭 선택) 직후, 메시지 응답 대신 `CharacterNameModal`(대표 캐릭터명 입력, 선택 사항)을 응답으로 띄우도록 `LinkStep2View.on_select` 변경. 모달 제출 시 입력값이 있으면 `set_main_character` 저장, 최종 확인 메시지에 시트 탭 + (입력했다면) 대표 캐릭터명을 같이 표시. 빈 채로 제출하면 기존처럼 시트 탭 이름으로 조회.
- `bot/utils/raid_signup.py` — `set_interest`(레이드당 캐릭터 1명, 덮어쓰기)를 `set_member_interests(guild_id, sheet_name, selections)`로 교체 — 이 사람의 관심 목록 전체(여러 레이드 × 레이드당 여러 캐릭터 가능)를 한 번에 통째로 교체하는 방식. 한 레이드에 메인/부캐를 둘 다 체크할 수 있게 됨(최종 배정 조율은 관리자 몫). `get_interest`/`get_all_interest`는 구조 그대로.
- `web/availability.py` — 캐릭터 조회 시 `get_main_character` 값이 있으면 그걸로, 없으면 기존처럼 `sheet_name`으로 `get_account_characters` 호출 → 결과를 아이템레벨 내림차순 정렬해서 상위 6개만 사용. `raid.interest_count`는 (엔트리 수가 아니라) 고유 인원 수로 계산하도록 수정. `POST /me/{token}/interest`는 그리드에서 만든 `interest_json`(`{raid_key,character,item_level}` 배열)을 받아 `set_member_interests` 한 번 호출로 저장.
  - **저장 시각 표시**: `set_last_saved(guild_id, sheet_name)`/`get_last_saved` 신규(member_link.py) — 가능시간·관심 레이드 둘 중 뭘 저장하든 마지막 저장 시각(KST, 분 단위)을 남김. 사용자가 "저장됐다는데 방금 바뀐 건지 아까 저장한 건지 모르겠다"고 피드백 → 저장 직후 배너뿐 아니라 페이지를 열 때마다 헤더 아래 항상 "마지막 저장: YYYY-MM-DD HH:mm"을 표시하도록 변경(리로드/재방문해도 확인 가능).
- `web/templates/availability.html` — "관심 있는 레이드" 섹션을 세로 카드 목록에서 그리드로 교체: 행 = 활성 레이드, 열 = 내 캐릭터(상위 6개, 레벨 높은 순). 칸 클릭으로 토글(가능시간 그리드와 같은 패턴), 레이드 최소 레벨 미달 캐릭터는 칸에 대각선 줄무늬(비활성, 클릭 무시) — 레벨 기준 자동 추천 역할. 제출 직전 JS로 체크된 칸들을 모아 히든 필드에 JSON으로 채워서 전송.

**검증**: 4개 파일 `py_compile` 통과, Jinja2 샘플 데이터 2가지 케이스(캐릭터 있음/없음) 렌더링 확인. 봇+웹 재시작 → 실제 사용자 토큰으로 라이브 확인: 대표 캐릭터 미등록 상태라 캐릭터 조회 실패 에러 메시지가 새 문구로 정상 노출되는 것 확인(그리드 자체는 캐릭터가 있어야 나오므로 실제 그리드 렌더는 샘플 데이터로 검증) — District_test 프로젝트 폴더에 임시로 복사한 정적 렌더 결과로 그리드 클릭/비활성 칸 무시/체크 해제/JS 직렬화(`interest_json`)까지 실제 클릭으로 확인 후 임시 파일 삭제. `POST /me/{token}/interest`에 curl로 직접 실제 데이터 넣어서 `set_member_interests` 저장 및 `last_saved` 갱신까지 실서버로 확인(테스트 데이터는 확인 후 제거, `last_saved`는 실사용 갱신값이라 그대로 둠). 실제 페이지에서 "마지막 저장: 2026-08-19 13:55" 표시되는 것도 스크린샷으로 확인.

**봇 재시작 필요**: 예 (`notice.py` 모달 로직 변경).
**웹 서버 재시작 필요**: 예 (`availability.py`, `raid_signup.py`, `member_link.py` 변경).

**미완료**: 실제 계정으로 대표 캐릭터명을 아직 등록 안 해서, 그리드 자체가 사용자 본인 화면에는 아직 안 뜸(캐릭터 조회 실패 상태) — 다음에 디스코드에서 "내 시트 연결"을 다시 진행해서 대표 캐릭터명을 입력해야 실제로 그리드가 보임. 관리자 화면(`admin_schedule.html`)의 컬럼 기반 `raid_signups`와 이번 `raid_interest`는 여전히 별개 데이터(기존에 남겨둔 한계, 이번 라운드에서도 통합 안 함).

### 로스트아크 API 진단 — 웹 프로세스 UnicodeEncodeError로 진짜 에러가 가려지고 있었음

**배경**: 사용자가 실제 캐릭터명("빛쟁인거니")을 대표 캐릭터로 등록하고 테스트했는데도 계속 "캐릭터 정보를 불러오지 못했습니다" 에러. `web/availability.py`가 `except Exception:`으로 넓게 잡고 있어서 진짜 원인이 안 보였음.

- `web/main.py` — 최상단에 `sys.stdout.reconfigure(encoding="utf-8")` 가드 추가(이전 세션에 `bot/main.py`에 추가했던 것과 동일한 수정, 웹 프로세스에는 빠져 있었음). Windows 콘솔이 cp949일 때 `lostark_api.py` 내부의 이모지 `print()`(`⚠️`, `❌` 등)가 `UnicodeEncodeError`로 죽으면서, 그 예외가 `except Exception:`에 걸려 진짜 API 에러 대신 항상 같은 안내 문구만 뜨고 있었음.
- 수정 후 실제 로그에서 확인된 진짜 원인: **`⚠️ API 에러 401: /characters/빛쟁인거니/siblings`** — 캐릭터명 문제가 아니라 API 키 자체가 거부되고 있었음.
- `bot/.env`의 `LOSTARK_API_KEYS` 값을 확인해보니 길이가 20자 안팎으로 매우 짧음. 실제 로스트아크 API 키(JWT)는 점(`.`)으로 구분된 세 구간으로 수백 자에 달함(`lostark_api.py`의 `_MIN_KEY_LEN = 100` 검증도 이 사실을 전제로 함) — **길드 자체 키가 아니라 `.env`의 전역 폴백 키가 잘려서 저장된 것으로 보임.**

**미해결(사용자 조치 필요)**: `bot/.env`의 `LOSTARK_API_KEYS`를 로스트아크 오픈 API 개발자 포털(`developer-lostark.game.onstove.com`, 이미 `bot/config/settings.py`의 `LOSTARK_API_BASE_URL`로 쓰이고 있는 도메인)에서 발급받은 **전체** 키로 다시 붙여넣어야 함. 키는 비밀값이라 Claude가 직접 발급/입력하지 않음 — 사용자가 직접 `.env` 파일을 열어 교체.

### 길드장이 볼 "길드 전체 가능시간" 히트맵 페이지 신규

**배경**: When2meet 참고 요청 때 언급됐던 "Group's Availability"(전체 취합 뷰)를 길드장이 볼 수 있는 별도 장소로 만들어달라는 요청.

- `web/admin.py` — `GET /admin/{guild_id}/group-availability` 신규. `member_link.get_all_availability`로 이번 주 전원의 가능시간 블록을 모아 7일×24시간 칸마다 "가능한 사람 이름 리스트"로 취합(`grid[day][hour] = [sheet_name, ...]`), 최대 인원수도 같이 계산해서 넘김. 기존 관리자 라우트와 동일하게 `_require_guild_access`로 로그인/권한 체크.
- `web/templates/group_availability.html` — 신규. 조회 전용 히트맵: 인원수가 많을수록 `color-mix()`로 초록이 진해짐(CSS `color-mix(in srgb, var(--support) N%, var(--card))`, 최신 Chromium 기준 정상 동작). 칸을 클릭하면 아래 패널에 "OO요일 N시~N+1시 · M명 가능 + 이름 목록" 표시. 편집 기능 없음(개인 페이지의 드래그 그리드와 달리 조회 전용).
- `web/templates/admin_schedule.html` — 상단 링크 줄에 "🗓 길드 전체 가능시간 보기 →" 추가(기존 "⏰ 요일별 시간 정책 설정 →" 옆).

**검증**: `py_compile` 통과, Jinja2 샘플 데이터 렌더링 확인 → 웹 서버 재시작 → 실제 길드 ID로 라이브 확인: 실제 저장된 "거니"의 가능시간이 정확히 히트맵에 반영되는 것, 칸 클릭 시 "수요일 7시~8시 · 1명 가능 / 거니"로 정확히 표시되는 것, `admin_schedule.html`에서 새 링크로 진입되는 것까지 스크린샷으로 확인.

**봇 재시작 필요**: 아니오. **웹 서버 재시작 필요**: 예.

**미완료(사용자 피드백, 다음에 색상 재검토)**: 지금 단색(초록) 스케일이라 (1) 0명/"안 됨" 칸이 눈에 잘 안 띄고, (2) 인원이 많아질수록 진해지는데 끝까지 가면 너무 진해져서 배경색(어두운 카드색)과 구분이 애매해짐(사실상 검은색처럼 보임). 다색 그라데이션이나 밝기 상한 조정 등으로 다음에 다시 손볼 것.

### 레이드 카탈로그 불일치 확인 — "카양겔 헬"은 실제 데이터가 아니었음

사용자가 "레이드에 카양겔 헬 같은 게 왜 있냐"고 확인 요청. 조사 결과:
- 실제 활성 레이드 카탈로그(`raid_config.get_active_raids`, 개인 페이지 "관심 있는 레이드" 그리드가 씀)에는 **카양겔이 전혀 없음** — 세르카(나이트메어/하드/노말), 종막(하드) 4개뿐.
- 사용자가 제공한 실제 길드 시트 엑셀 내보내기(`주간레이드` 탭)와 대조해도 카양겔은 등장하지 않음(벨가/성당/세르카/종막/4막/3막/2막/종겜 계열만 존재) — 파싱 로직 자체는 정상.
- **결론**: "카양겔 헬"은 이전 라운드에서 그리드 UI를 검증할 때 Claude가 임시로 만든 샘플 테스트 파일(공유 브라우저 창에 잠깐 떴던 정적 파일, 검증 직후 삭제함)에 들어있던 가상의 예시 데이터였음 — 실제 시스템/시트에는 반영된 적 없음.
- **별개로 발견한 진짜 이슈**: `admin_schedule.html`(실시간 시트 컬럼 파싱, `sheets.parse_all_raids`)과 `get_active_raids`(별도 활성화 카탈로그, `raid_config.py`)가 서로 다른 레이드 목록을 보여주고 있음 — 예: 관리자 화면엔 "카멘 노말", "벨가르딘 노말"이 보이는데 개인 페이지 관심 레이드 그리드엔 없음. 이 둘을 어떻게 맞출지는 아직 사용자 확인 전이라 손대지 않음.

### 레이드 카탈로그 실제 반영 — 벨가르딘 추가, 활성 레이드 재구성

사용자 확인 후 진행. `bot/data/raid_data.json`(게임 레이드 마스터 카탈로그)에 "벨가르딘"이 통째로 없어서 활성화 자체가 불가능했던 문제 — 실제 시트엔 이미 신청자가 있는 상태였음(벨가나메1에 8명).

- `bot/data/raid_data.json` — 벨가르딘 추가(그림자 레이드, 세르카 다음 단계). 노말 1750 / 하드 1770 / 나이트메어 1780, 8인 파티, 기본 소요시간 60분. 레벨은 실제 시트 "특이사항" 행 값 그대로, 사이즈 8은 실제 시트의 "인원수"가 8까지 찍힌 것(4인이면 불가능한 수치) + 관리자 화면 "0/8" 배지로 교차 확인.
- `bot/data/guild_settings.json`(해당 길드) — 벨가르딘 3난이도 전부 활성화. 이어서 사용자 확인 하에 4막(노말+하드)도 활성화, 성당(1/2/3단계)도 활성화. 서막/1막/2막/3막 및 그 아래(카양겔/상아탑/발탄/비아키스/쿠크세이튼/아브렐슈드/일리아칸/카멘/베히모스)는 애초에 이 길드에서 활성화된 적이 없어서(never configured) 별도 조치 불필요 — "보류" 상태를 원했는데, 사용자 확인 결과 새 상태를 만들 필요 없이 지금의 비활성화(미설정)로 충분하다고 함.
- **최종 활성 레이드(레이드명 기준 5개)**: 벨가르딘·세르카·성당·종막·4막 (난이도는 각각 다 같이 켜짐).

**검증**: `raid_data.json` JSON 파싱 확인, 봇+웹 재시작 후 `get_active_raids()` 라이브 확인, 개인 페이지 관심레이드 그리드에 실제로 반영되는 것까지 확인. `guild_settings.json`만 바꾼 항목(4막/성당 활성화)은 봇/웹 재시작 없이도 즉시 반영됨을 확인(매 요청마다 파일을 새로 읽으므로) — `raid_data.json` 변경(벨가르딘 신규 추가)은 모듈 임포트 시점에 캐싱돼서 재시작 필요했음.

**봇 재시작 필요**: 벨가르딘 추가 시점엔 예(카탈로그 캐싱). 이후 4막/성당 활성화는 아니오.

### 가능시간 그리드 "세밀 설정" — 30분 단위 토글

**배경**: 기본은 1시간 단위 칸(24개)이 편하지만, 필요하면 30분 단위(48개)로 더 세밀하게 칠하고 싶다는 요청. "길드장이 설정" 관련 아이디어(요일별 30분/1시간 기본값 지정, 새벽 시간대 자체를 그리드에서 제외 등)는 이번엔 범위에서 뺐고, 우선 개인이 그 자리에서 토글하는 버튼만 구현.

- `web/templates/availability.html` — 그리드 툴바에 "🔍 30분 단위로" 버튼 추가. JS를 `slotsPerHour`(1 또는 2) 기준으로 슬롯 개수/시각 변환을 계산하도록 재작성 — 칸 데이터 속성을 `data-hour`(정수 시)에서 `data-slot`(그 단위의 인덱스)으로 바꾸고, 저장 시 `slot/slotsPerHour`로 실제 시각(소수 가능, 예: 6.5시)으로 환산. 토글 버튼을 누르면 현재 칠해진 칸을 실제 시각 블록으로 먼저 뽑아둔 뒤 슬롯 수를 바꾸고 다시 칠해서, 30분↔1시간 왕복해도 칠한 내용이 유지됨(반올림으로 손실 가능 — 30분 단위로 칠한 걸 1시간으로 내리면 30분 단위 정밀도는 사라짐, 다시 30분으로 올리면 시간 단위로 복원됨).
- `web/availability.py` — `submit_availability`가 `start`/`end`를 `int()`가 아니라 `float()`로 파싱하도록 변경(30분 단위 값 0.5 허용).

**검증**: Jinja2 렌더링 확인 → 웹 서버 재시작 → 실제 사용자 토큰으로 라이브 확인: 버튼 클릭 시 168칸(7×24)→336칸(7×48) 전환 확인, 30분 칸 하나 칠하고 1시간으로 되돌렸을 때 해당 시간대가 정확히 켜진 상태로 보존되는 것, 다시 30분으로 돌렸을 때도 원래 칠한 칸이 그대로 복원되는 것까지 JS로 직접 확인(제출은 안 해서 실제 저장 데이터는 안 건드림).

**봇 재시작 필요**: 아니오. **웹 서버 재시작 필요**: 예.

**미완료**: "길드장이 기본 단위를 지정"하거나 "새벽 시간대를 아예 제외"하는 건 이번에 범위 밖으로 뺌 — 필요해지면 다음에.

### 저장소 공통화 + 동시쓰기 안전장치 + 자동 백업

**배경**: `load_settings()`/`save_settings()` 패턴이 13개 파일(`bot/cogs/admin.py, notice.py, party.py, raid_config.py, raid_manage.py, schedule.py, schedule_view.py, setup.py`, `bot/utils/favorite_links.py, guild_link.py, lostark_api.py, member_link.py, raid_signup.py, web_results.py`)에 각자 복붙돼 있었음. 봇 프로세스와 웹 프로세스가 `guild_settings.json`을 동시에 읽고 쓰는데 파일 잠금이 전혀 없었고, 백업도 없어서 파일 손상 시 전체 길드 데이터 유실 위험이 있었음.

- `bot/utils/storage.py` — 신규. `load_settings()`/`save_settings()`를 한 곳으로 모으고:
  - **원자적 쓰기**: 임시 파일(`.tmp`)에 먼저 쓰고 `os.replace()`로 교체 — 쓰다가 죽어도 기존 파일이 반쪽으로 안 깨짐(POSIX/Windows 둘 다 원자적).
  - **파일 잠금**: 단순 락 파일 방식(`.lock`), 쓰는 순간만 직렬화. 5초 넘게 안 풀리면(비정상 종료로 락이 안 풀린 경우) 강제 진행.
  - **자동 백업**: 저장할 때마다 `bot/data/backups/guild_settings_TIMESTAMP.json` 남기고 최근 30개만 유지.
- 위 13개 파일 전부 자체 정의를 지우고 `from bot.utils.storage import load_settings, save_settings`(또는 `_load`/`_save` alias)로 교체. 기존 호출부 코드는 손대지 않음(순수 import 교체라 동작 변화 없음).
- `bot/utils/lostark_api.py`의 `_resolve_keys()`도 같은 방식으로 정리.

**알려진 한계**: 지금 방식은 "쓰는 순간"만 겹치지 않게 할 뿐, `load → 수정 → save` 사이 구간까지 완전히 직렬화하는 진짜 트랜잭션은 아님 — 두 프로세스가 동시에 같은 데이터를 읽고 각자 다르게 고친 뒤 저장하면 나중에 저장한 쪽이 이길 수 있음(lost update). 완전히 막으려면 호출부마다 "락 안에서 load/save까지 다 하는" 패턴으로 바꿔야 하는데, 지금 규모(길드 몇 개, 동시 저장 드묾)에선 과한 작업이라 다음 단계로 미룸. 대신 원자적 쓰기+백업으로 "파일이 깨지는" 최악의 시나리오는 확실히 막았고, 문제 생겨도 백업에서 복구 가능.

**검증**: 13개 파일 + `storage.py` 전부 `py_compile` 통과. `bot.cogs.*`/`bot.utils.*`/`web.admin`/`web.availability`/`web.main` 전체 18개 모듈 실제 임포트 확인(순환참조 등 문제 없음). 봇+웹 재시작 → 전체 cog 정상 로드 확인 → 실제 웹 프로세스에서 공대 배정 토글(써보기) → `bot/data/backups/`에 백업 생성되는 것 + `guild_settings.json`에 정상 반영되는 것 + 되돌리기까지 실제로 확인.

**봇 재시작 필요**: 예. **웹 서버 재시작 필요**: 예 (둘 다 완료).

- `get_user_schedule()`/`get_weekly_summary()` — 개인/전체 일정 이미지 렌더링(`image_renderer.py`)에 그대로 넣을 수 있는 형식으로 데이터 조립.

**`bot/cogs/party.py`**: url/data를 여기저기로 넘기던 구조를 전부 걷어내고 `guild_id` 하나로 통일(생성자 시그니처들 단순해짐). 이름/난이도가 분리되면서 생긴 부수 효과 두 가지 수정:
- 예전엔 "카멘(하)2"처럼 이름에 공대 번호가 박혀있어서 자동으로 구분됐는데, 이제 이름이 "카멘"만 남아서 **같은 레이드+난이도 공대가 여러 개면 편성 결과가 서로 덮어써지는 버그**가 될 뻔한 걸 미리 발견 — 표시할 때 "카멘 하드 1", "카멘 하드 2"처럼 자동으로 번호를 붙이게 수정.
- 재편성 버튼들이 레이드를 이름으로 찾다가(이제 난이도 없이는 특정이 안 됨) 고장 날 뻔한 것도 컬럼(col) 기준 매칭으로 수정.
- AI 자동편성 결과를 시트의 "AI편성결과" 탭에 로그로 남기던 기능은 삭제(아무도 다시 안 읽던 죽은 기능이었음 — 결과는 이미 디스코드 스레드+웹 링크로 충분히 공유됨).

**`bot/cogs/schedule_view.py`**: "주간레이드 탭 / AI편성 탭" 둘 중 골라서 보던 방식 자체가 시트 시절 개념이라 통째로 제거(이제 데이터 소스가 하나뿐이라 고를 게 없음) — 관련 버튼("📋 주간레이드 탭", "🤖 AI편성 탭", "🤖 AI편성→주간레이드 복사")도 삭제, "내 일정 보기"/"전체 일정 보기" 흐름 단순화.

**`bot/cogs/schedule.py`**: `/이번주갱신`이 여전히 시트를 읽고 있던 걸 `raid_schedule.get_weekly_summary()`로 전환. 이제 이 명령어는 "시트→디스코드 동기화" 개념이 아니라 그냥 "주간 일정 이미지 지금 바로 다시 그리기"가 됨(웹 편집이 이미 실시간으로 같은 데이터에 반영되므로).

**`bot/utils/sheets.py` 대폭 정리**: 960줄 → 약 100줄. 레이드 CRUD/파싱/AI편성 관련 함수 전부(add_raid, update_raid, delete_raid, parse_raids, parse_all_raids, get_members, get_user_schedule, get_weekly_summary, get_raid_members_by_availability, assign_raid_times, save_assigned_times, copy_ai_to_manual 등 20여 개) 삭제 — 전부 raid_schedule.py/raid_signup.py로 대체되어 완전히 죽은 코드였음. 남은 건 레이드 카탈로그 조회 헬퍼(순수 JSON)와 `get_sheet_info`(닉네임 등록용 시트 탭 목록 조회)뿐. `get_sheet_info`도 "주간레이드" 탭이 있어야만 동작하던 하드코딩을 제거 — 이제 시트에 그 탭이 아예 없는 새 길드도 닉네임 등록이 문제없이 됨.

**검증**: 전체 py_compile + `bot.cogs.*`/`bot.utils.*`/`web.main` 임포트 전부 통과. 실제 길드 데이터로 개별 함수 단위 검증 — `assign_raid_times`가 실제 48개 공대를 크래시 없이 처리(이번 주는 아무도 가능시간을 아직 안 내서 전부 "미정"으로 나오는 것까지 정상 확인 — 주차가 막 바뀐 시점이라 예상된 결과). `get_raid_candidates`가 실제 캐릭터/직업/서폿 정보를 정확히 반환. `get_user_schedule`/`get_weekly_summary`로 실제 데이터 기반 이미지 3종(개인 일정, 주간 카드, 주간 타임라인) 전부 렌더링 성공. `save_assigned_times` 실제 쓰기→읽기 확인 후 원상복구까지 확인. 봇+웹 재시작 후 `/admin/{길드}/schedule` 살아있는 것도 재확인.

**봇 재시작 필요**: 예 — 완료함. **웹 서버 재시작 필요**: 예 — 완료함(이번 참에 같이).

**결과**: 시트→JSON 마이그레이션 1~3단계 전부 완료. 이제 레이드 일정과 관련해서 웹/디스코드가 정확히 같은 데이터를 보고, 구글 시트는 닉네임 등록(개인 탭 목록 조회) 하나에만 남아있음. 다음은 이 위에 AI 자동편성 웹 UI를 실제로 만드는 작업.

### AI 자동편성 웹 UI 신규

**배경**: 디스코드에서만 되던 "🤖 자동 편성"(주간 전체 편성)을 웹 대시보드에도 만듦 — 2·3단계에서 이미 `raid_schedule.assign_raid_times()`가 완전히 JSON 기반으로 분리돼 있어서, 그 위에 웹 화면만 새로 얹으면 됐음.

**흐름 (`/admin/{guild_id}/compose`):**
1. 예정된 레이드 목록에서 편성할 레이드 체크(전체선택/해제 버튼 있음) → "자동 편성 실행"
2. 결과 미리보기 — 레이드별 배정 시간, 파티 구성(파티1/파티2, 캐릭터·서폿 표시), 시간 배정 실패(가능시간 안 겹침)나 다른 레이드와 시간 충돌은 경고로 표시. **이 단계에서는 아직 아무것도 저장 안 됨.**
3. 저장할 레이드만 체크(시간 배정 안 된 건 자동으로 체크 해제) → "전체 저장" → 그 시간으로 예정 처리

디스코드 쪽과 마찬가지로 파티 구성(누가 몇 번 파티인지) 자체는 별도 저장 안 함 — 그 자리에서 확인만 하고 넘어가는 정보이고, 실제 참가자는 일정 관리 화면의 배정 목록이 기준.

**신규**: `web/admin.py`에 라우트 3개(`GET /compose`, `POST /compose/run`, `POST /compose/save`), 템플릿 2개(`compose_select.html`, `compose_results.html`), `guild_home.html`에 "🤖 AI 자동편성" 카드(관리자 전용) 추가.

**검증**: 실제 길드 데이터로 전체 플로우 테스트 — 레이드 선택 → 편성 실행 → 결과 미리보기(체크박스·hidden 필드 정상 생성 확인) → 저장 → 실제로 레이드가 그 시간으로 "예정" 전환되는 것까지 확인(가짜 가능시간을 임시로 넣어서 실제로 시간이 배정되는 경우까지 검증 후 원래 데이터로 복원). 웹 서버 재시작 후 페이지 로드 확인.

**봇 재시작 필요**: 아니오. **웹 서버 재시작 필요**: 예 — 완료함.

**남은 것**: 시너지 분석(⚡)은 아직 디스코드 전용. AI 코멘트(Gemini)·평균 전투력 조회 같은 부가 기능도 웹에는 아직 없음 — 필요하면 다음에.

### 초기 등록용 엑셀 업로드(레이드+멤버 일괄 등록) 신규

**배경**: 시트를 버리고 나니 "레이드 하나씩 웹에서 추가", "멤버 하나씩 `/닉네임등록`" 하는 게 최초 세팅 시엔 너무 번거로움 — 특히 레이드 수십 개, 멤버 수십 명을 처음부터 하나씩 넣는 건 비효율적이라는 지적. 시트를 다시 라이브 연동으로 쓰면 오늘 없앤 바로 그 번거로움(서비스 계정 공유, URL 등록)이 되살아나므로, 대신 **엑셀 파일 하나를 그때그때 업로드해서 파싱만 하는 방식**으로 설계.

**흐름**:
1. `.xlsx` 하나에 시트 탭 "레이드"/"멤버" (탭 이름에 해당 글자만 포함되면 인식) — 레이드 탭은 레이드명/난이도(필수) + 요일/시간/소요시간(선택), 멤버 탭은 닉네임(필수) + 캐릭터명(선택)

4. 각 멤버가 나중에 `/닉네임등록` 하면 명단에서 본인 이름을 골라 클릭 한 번으로 본인 계정에 연결(claim) — 직접 타이핑 안 해도 되고 오타 걱정도 없음. 명단에 없으면 기존처럼 직접 입력 모달로 폴백.

- 템플릿 3개 (`members.html`, `import_upload.html`, `import_preview.html`), `guild_home.html`에 "👥 길드원 명단" 카드 추가

**검증**: 실제 길드 데이터로 전체 플로우 테스트 — 가짜 레이드 2개/멤버 2개(중복·빈칸 포함)를 담은 엑셀을 실제로 만들어서 업로드 → 미리보기(에러 표시 확인) → 확정(레이드 등록·미청구 명단 저장 확인) → claim 성공/중복 claim 거부까지 확인 후 테스트로 넣은 데이터 전부 원상복구. 웹 서버·봇 둘 다 재시작해서 반영 확인.

### 시너지 파티 추천 + 길드 코드 위치 이동 + 레이드 목록 가시성 개선

**시너지 분석에 파티 추천 추가**: 빠진 필수 시너지마다 "이 직업 중 하나 추가하면 채워짐" 후보를 같이 보여줌 — `synergy_benefits.json`의 `providers` 데이터를 그대로 재사용, 이미 선택된 직업은 후보에서 제외. 후보가 너무 많으면(예: 방어력 감소류는 제공 직업이 10개 넘음) 6개까지만 보여주고 "외 N개"로 축약.

**검증**: 브라우저로 실제 렌더링 확인 — 레이드별 아이콘 색상이 이름 기준으로 일관되게 나오는지(종막 계열 전부 동일 색), 난이도 배지 색상 구분, 실제 존재하는 클리어 레이드("예비용") 하나로 초록 틴트+뱃지 정상 표시 확인. 시너지 페이지도 실제 선택값으로 추천 문구 렌더 확인.

### 일정 관리 아코디언(그리드) 레이아웃 실제 적용 + 권한→웹 수정권한 연동

**아코디언 레이아웃**: 비교 시안 중 "아코디언(레이드명 기준)" 채택 확정 — 레이드명으로 묶어서 그룹당 하나의 카드로, "미정" 공대는 기본 접힘. 여기서 한 걸음 더 — "꼭 위→아래 스크롤이어야 하냐, 카드처럼 여러 열로 못 하냐"는 질문에 맞춰 그룹 카드들을 `grid-template-columns: repeat(auto-fit, minmax(340px,1fr))`로 배치, 넓은 화면(1300px+)에서 최대 3열까지 자동으로 늘어남. 모바일은 1열 유지. 기존 기능(수정/공대추가/클리어/삭제/예정토글, 추천 시간대)은 전부 그대로 유지 — 그룹 안에 개별 공대 카드(`squad-row`)로 옮겨졌을 뿐 로직 변경 없음.

**권한 → 웹 수정권한 연동**: 디스코드 서버 관리자 권한이 없어도, 로일 자체에 "길드장"/"부길드장"으로 등록(`get_role`)된 사람이면 `/admin/{guild_id}` 수정 권한을 인정하도록 `_admin_guilds()`에 로직 추가 — 등록된 전체 길드를 훑어서 role이 매칭되면 admin_guilds에 편입. `_require_guild_access`/`_require_view_access`/`/admin` 단일 길드 자동 리다이렉트까지 전부 이 함수 하나에서 파생되므로 별도 수정 없이 다 같이 적용됨.

**검증**: 실제 디스코드 OAuth 로그인 성공 확인(오늘 처음 실제 크리덴셜로 테스트) — 로그인 후 자동으로 유일하게 매칭되는 길드로 이동하는 것까지 실제로 확인함. 권한 연동은 가짜 유저에게 "부길드장" role만 부여(디스코드 관리자 권한은 없는 상태)하고 접근 가능한지/무관한 유저는 여전히 막히는지 직접 함수 호출로 검증. 아코디언 그리드는 실제 페이지 렌더링 + 클릭 토글 동작(그룹 접기/펴기, 미정 목록 펴기)까지 브라우저로 확인, 데스크탑 3열/모바일 1열 둘 다 확인.

**중요 발견**: 이 과정에서 `python -c` 같은 임시 스크립트로 `bot.config.settings`를 테스트할 때 `find_dotenv()`가 cwd에 있는 루트 `D:\LOIL\.env`(빈 파일)를 잘못 찾아가는 걸 발견 — 실제 `python -m uvicorn`/`python -m bot.main`으로 정식 실행할 때는 정상적으로 `bot/.env`를 찾아서 문제없음. 다만 앞으로 설정값을 빠르게 확인하고 싶을 때 `python -c`로 단독 테스트하면 헷갈릴 수 있음 — 실제 실행 방식(`-m` 모듈 실행)으로 확인해야 함.

**봇 재시작 필요**: 아니오(권한 로직은 web/admin.py만 해당). **웹 서버 재시작 필요**: 예 — 완료함. (겸사겸사 예전에 안 죽은 채 남아있던 봇 프로세스 중복 실행도 발견해서 정리함.)

### "인원수" 필드를 죽은 값에서 실제 공대별 목표 인원으로 전환

**배경**: 저번에 발견한 죽은 "인원수" 필드를 그냥 없애려다가, 다시 생각해보니 진짜 필요한 기능이었음 — 8인 레이드라고 항상 8명이 가는 게 아니라 4명이나 2명만 모아서 갈 수도 있는데, 그런 경우 "정원"을 관리자가 직접 정할 수 있어야 완료 여부(N/정원) 판단이 정확해짐.

**변경**: 레이드 인스턴스마다 `size_override`(선택) 필드 추가 — 있으면 그 값을, 없으면 기존처럼 레이드 카탈로그 기준값을 씀. "새 레이드 추가" 모달과 공대별 "수정" 폼 둘 다에 "목표 인원수" 입력란(빈칸=자동) 추가, 비우면 다시 카탈로그 기준으로 돌아감. 직접 지정한 공대는 "N/정원*" 처럼 별표로 표시해서 자동값이 아니란 걸 구분.

**신규/변경**: `raid_schedule.py`의 `_enrich`/`add_raid`(size_override 파라미터), `web/admin.py`의 `add_raid_route`/`update_raid_route`(size 폼 필드 파싱), `confirm_conflict.html`(트라이 충돌 재확인 시 size 값 유지). 이제 안 쓰는 `RAID_SIZES`/`raid_sizes` 드롭다운 목록도 정리.

**검증**: 8인 레이드를 목표 4명으로 새로 등록 → size=4 저장 확인 → 수정에서 비워서 자동(8명)으로 복귀 확인 → 다시 2명으로 변경 확인 → 실제 페이지에 "목표 인원수" 필드 노출까지 확인 후 테스트 데이터 원상복구.

### 파티 분할 로직을 "몇 명이든" 정확히 처리하도록 일반화 + "풀팟" 표시

### 시너지 분석을 실제 편성 불러오기 기반으로 재설계

**배경**: 지금까지 시너지 분석은 완전 수동(체크박스로 직업 하나하나 고르는) 방식이었는데, 사용자 지적 — 이건 실제 파티 구성이랑 완전히 분리된 "단편적인" 정보라 이 상태로는 탭 하나 만들 가치가 크지 않다는 것. 진짜 필요한 건 (1) 실제 등록된 레이드의 실제 편성 인원을 그대로 불러와서 바로 분석하고, (2) 거기에 길드원 아닌 게스트를 추가로 얹어서 "이 자리에 이런 직업이 들어오면 어떨지" 커스텀으로 볼 수 있는 것. 서폿은 시너지 매칭 대상이 아니라(고정 버프 제공) 실질적으로 딜러끼리 각인 조합 맞추는 게 핵심이라는 점도 확인.

### "이미 시작하셨나요?" 카드가 눈에 안 띄던 문제 — 색 대비 강화

**배경**: "봇 추가는 잘 되는데, '이미 시작하셨나요?' 섹션이 눈에 안 띈다"는 피드백. 원인 확인 — 처음 넣은 버전은 카드 배경을 `.feat-card`와 똑같이 중립색(`var(--card)`)에 왼쪽 테두리만 살짝 준 정도라, 특히 다크 모드에서 배경(`#0d0f14`)과 카드색(`#161922`)의 명도 차이가 너무 작아서 사실상 안 보이는 수준이었음.

**변경** (`web/templates/index.html`, `docs/index.html` 둘 다 동일 적용): `.start-card` 배경을 중립색 대신 파란색 틴트(`rgba(79,99,210,.14)`, 호버 시 `.22`)로 바꾸고 테두리도 `var(--accent-bd)`+왼쪽 4px `var(--accent)`로 강화 — 이제 카드 자체가 "AI 파티 자동편성" 같은 일반 기능 카드와는 확실히 다른, 파란 틴트가 도는 강조 카드로 보임. 정리하다 보니 예전 `.start-card:hover`가 중복 선언되어(뒤 선언이 앞의 강화된 hover 효과를 덮어써서 무효화하던 버그) 있던 것도 같이 제거.

**검증**: 스크린샷 도구가 이 세션에서 캡처 글리치를 일으켜서(새 탭에서도 전체가 까맣게만 나옴 — nav까지 안 보임) 화면 캡처로는 직접 확인 못 했지만, `get_page_text`로 전체 페이지 텍스트/구조가 정상 순서로 다 있는 것 확인, JS `getComputedStyle`로 `.start-card` 배경이 실제로 `rgba(79,99,210,.14)`, 테두리가 `rgb(79,99,210)` 4px로 정확히 적용된 것 확인. 실제 화면 확인은 사용자가 직접 브라우저로 재확인 필요.
