# 2026-08-03 — 로일 메인 페이지 + 길드 코드 가입 구조 (설계, 코드 착수 전)

## 사용자가 설명한 그림 (제가 이해한 대로 재정리)

1. **로일(LoIl) 메인 페이지** (`/` — 지금 있는 `index.html` 활용) — 로일이 뭐고 어떻게 쓰는지 설명하는 단일 진입점. 길드마다 따로 노는 페이지가 아니라, 전체 서비스의 "집".
2. **길드 탭/페이지** — 여기서 두 갈래:
   - **코드로 가입**: 이미 있는 길드 그룹에 코드를 입력해서 들어감(가입 신청 성격 — 관리자가 코드를 알려줌).
   - **길드 그룹 생성하기**: 새로 시작.
3. 지금 하고 있는 "봇 설정"(디스코드 연동, 시트 URL 등록 등)을 이 흐름 안에 배치.
4. 길드마다 세션이 많이 생길 텐데(멀티테넌시), 그때 생기는 문제를 미리 찾아두는 게 중요하다고 강조.
5. 디스코드에 봇이 이미 들어가 있으면, 봇이 주는 링크를 타고 들어가면 그 길드의 작은 홈페이지가 뜨는 것도 고려.

## 지금 이미 있는 것과 겹치는 부분 — 먼저 정리해야 할 충돌 지점

| 지금 있는 것 | 새로 제안된 것 | 관계를 정해야 함 |
|---|---|---|
| Discord OAuth2 로그인 → "이 유저가 관리자 권한 가진 길드" 자동 판별(`web/auth.py`) | 코드 입력으로 길드 가입 | **둘 다 유지? 코드가 OAuth를 대체?** OAuth는 "이 사람이 진짜 그 서버 관리자인지"를 디스코드가 보증해주는 것과 코드 입력은 "코드를 아는 사람은 다 들어옴"이라 신뢰 수준이 다름 |
| `guild_settings.json`에 길드가 등록되는 시점 = 디스코드 봇이 서버에 초대되고 `/봇설정`으로 시트 URL 등록할 때 | "길드 그룹 생성하기"를 웹에서 먼저 하는 흐름 | **웹에서 먼저 만들고 나중에 봇을 초대하는 순서도 지원?** 아니면 봇 초대가 먼저고 웹의 "생성하기"는 사실상 그 이후 설정 단계? |
| `/g/{slug}` — 편성 결과 공개 링크(길드별 고유 URL) | "길드 코드" | **slug랑 코드가 같은 것? 다른 것?** slug는 URL에 박히는 긴 랜덤 문자열이라 코드(사람이 타이핑하기 쉬운 짧은 코드)랑 목적이 다를 수 있음 |

## 멀티테넌시 관점에서 미리 짚어야 할 문제 (코드 짜기 전에)

- **코드의 신뢰 수준**: 코드만 알면 누구나 "가입 신청"이 되는지, 아니면 관리자가 승인해야 진짜 멤버가 되는지. 코드가 유출되면 낯선 사람이 우리 길드 데이터(일정 등)를 볼 수 있는 것 아닌지.
- **한 명이 여러 길드에 속하는 경우**: 디코 유저 하나가 여러 길드(부캐 길드 등)에 속할 수 있음 — 로그인 세션에 "지금 어느 길드로 보고 있는지" 상태를 어떻게 유지할지(지금은 `_admin_guilds`가 길드 목록을 세션에 다 들고 있는 정도).
- **코드 발급/재발급/만료**: 코드가 영구적인지, 주기적으로 바뀌는지(바뀌면 옛날 코드로 못 들어옴 — 유출 대응은 됨).
- **봇 링크로 들어왔을 때의 "작은 홈페이지"**: 이게 `/g/{slug}`(이미 있음, 로그인 없이 조회)를 그대로 쓰는 건지, 아니면 완전히 새로운 화면인지.

## 지금 할 수 있는 것 / 아직 결정이 필요한 것

**바로 할 수 있음 (구조만 있으면 되는 부분)**
- `index.html`(로일 메인)에 사용법/배경 설명 채우기 — 지금은 거의 비어있음, 콘텐츠만 있으면 됨
- 길드 홈(`guild_home.html`, 방금 만든 관리자용 허브)과 로일 메인을 연결하는 네비게이션

**결정 필요 (코드 짜기 전에 답이 있어야 하는 것)**
1. 코드 가입이 OAuth2 로그인을 **대체**하는지 **보완**하는지
2. 코드의 신뢰 수준(입력만 하면 바로 멤버 vs 관리자 승인 필요)
3. "길드 그룹 생성하기"가 봇 초대보다 **먼저** 올 수 있는지 (지금 구조는 봇 초대가 항상 먼저)
4. `web_slug`(공개 조회 링크)와 "길드 코드"(가입용)를 같은 값으로 쓸지 분리할지

## 사용자 결정 (2026-08-03)

1. **코드 vs OAuth**: 보완 관계. 관리자(길드장/부길드장)는 여전히 Discord OAuth2로 로그인. 코드는 일반 길드원 전용 가입 경로.
2. **코드 신뢰 수준**: 코드 입력 = 가입 신청. 관리자 승인이 있어야 진짜 멤버가 됨(즉시 멤버 아님) — "대기 중인 가입 신청" 목록과 승인/거절 UI가 필요.
3. **생성 순서**: 웹에서 "길드 그룹 생성하기"를 봇 초대보다 먼저 할 수 있어야 함.
4. **코드 vs slug**: 분리. `web_slug`(공개 조회 링크, 긴 랜덤 문자열)는 그대로 두고, "길드 코드"는 사람이 치기 쉬운 짧은 별도 값으로 새로 발급.

## 새로 발견된 문제 — 봇 초대 전 길드 식별자

지금 구조는 길드 하나 = **Discord 서버 ID**로 식별(`guild_settings.json`의 최상위 키가 전부 실제 디스코드 길드 ID). "웹에서 먼저 생성"을 지원하면, 그 시점엔 아직 봇이 어느 서버에도 안 들어가 있어서 **디스코드 길드 ID 자체가 존재하지 않음**. 그래서:
- 웹 생성 시 임시 ID(예: `web_` 접두사 + 랜덤값)를 발급해서 `guild_settings.json`에 "가(假) 등록" 상태로 저장해야 함.
- 이후 실제 디스코드 서버에 봇을 초대하고 연결 절차(코드 입력 등)를 거치면, 그 임시 등록을 실제 디스코드 길드 ID로 옮겨 붙이는(마이그레이션) 절차가 필요함 — 이게 없으면 웹에서 미리 설정한 것들(레이드 카탈로그, 시간 정책 등)이 붕 뜸.
- 이 연결 방법 자체가 어쩌면 "길드 코드"의 진짜 용도일 수 있음 — 즉, 웹에서 만든 임시 길드가 코드를 발급하고, **봇을 초대한 뒤 디스코드에서 그 코드를 입력하면 임시 길드와 실제 서버가 연결**되는 식.
- **결정**: 봇이 서버에 들어가면(on_guild_join) 봇이 "연결 코드 명령어"(예: `/길드연결 ABC123`)를 안내 → 관리자가 웹에서 만든 임시 길드의 연결 코드를 입력 → 임시 길드 데이터(레이드 카탈로그, 시간 정책 등)를 실제 디스코드 길드 ID로 옮겨 붙임. **가입용 "길드 코드"(일반 길드원용)와는 다른, 별도의 "연결 코드"**임 — 총 세 종류의 코드/식별자가 생기는 셈: ①일반 길드원 가입 코드 ②임시→실제 서버 연결 코드 ③`web_slug`(공개 조회 URL용). 이름이 헷갈리기 쉬우니 구현 시 세 개를 명확히 구분해서 부를 것.

## 구현 순서 제안 (다음 라운드)

1. **데이터 모델**: `guild_settings.json`에 "임시 길드"(`web_`-접두사 ID, `pending=True`) 상태 지원 추가.
2. **웹**: 로일 메인(`/`)에 사용법/소개 채우기 + "길드 그룹 만들기" 진입점.
3. **웹**: 길드 그룹 생성 폼(길드명 입력 정도로 최소화) → 가입 코드 + 연결 코드 동시 발급.
4. **웹**: 가입 코드 입력 화면 → "가입 신청" 등록(대기 상태) + 관리자 승인/거절 UI(관리자 허브에 추가).
5. **봇**: `on_guild_join` 이벤트에 연결 코드 안내 메시지 추가 + `/길드연결 코드` 명령어로 임시→실제 병합 로직.

이번 세션에서 오늘 이미 많은 작업을 했고 이 기능 자체가 새 데이터 모델(대기 상태, 승인 큐)이 필요한 규모라 바로 코드 짜기보다 다음 라운드로 넘기는 걸 제안 — 사용자 확인 필요.

## 별도로 확인된 것 (즉시 반영 예정)
사용자가 명확히 답변: 특정 레이드에 실제로 몇 명이 가는지는 **개인 가능시간 제출 화면(`/me/{token}`)에서 이번 주 "불참" 표시를 안 한 사람 = 이번 주 참여자**로 판단하면 됨. 기존에 쓰던 "시트에 등록된 전체 인원 중 결석 아닌 사람" 카운트보다 이 데이터가 더 정확한 신호 — 다음에 파티 수 힌트를 보여줄 때 이 데이터를 우선 참고하도록 반영 예정.
